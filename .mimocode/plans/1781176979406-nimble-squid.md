# 3 Landing Pages para Google Ads — Plano de Implementação

> **Para agentes:** REQUIRED SUB-SKILL: Use compose:subagent ou compose:execute para implementar este plano.

**Objetivo:** Criar 3 landing pages focadas em diferentes campanhas de Google Ads, cada uma com URL, conteúdo e chamada para ação distintos.

**Arquitetura:** Cada página usa o mesmo layout (PublicNavbar + Footer), mas com ordenação de secções e copy diferente. As secções existentes (HeroSection, FeaturesSection, etc.) são reutilizadas. Novos namespaces i18n fornecem o conteúdo específico de cada campanha.

**Tech Stack:** Wasp routes + React + i18next (3 novos namespaces)

Cada componente usa o namespace i18n correspondente e define a ordenação de secções adequada ao foco da campanha.

- [ ] **Step 1: Criar LandingSistema.tsx** — secções na ordem: Hero, Features (attendance primeiro), Personas, Steps, Pricing, FAQ, CTA

```tsx
import { useTranslation } from 'react-i18next';
import { PublicFooter } from '../catequese/PublicFooter';
import { PublicNavbar } from '../catequese/PublicNavbar';

export default function LandingSistema() {
  return (
    <div className="min-h-screen flex flex-col bg-background">
      <PublicNavbar />
      <main className="flex-1">
        <HeroSection namespace="landingSistema" />
        <FeaturesSection namespace="landingSistema" order={["attendance","dashboard","family","sacraments","library","ai"]} />
        <PersonasSection namespace="landingSistema" />
        <StepsSection namespace="landingSistema" />
        <PricingPreviewSection namespace="landingSistema" />
        <FaqSection namespace="landingSistema" />
        <CtaSection namespace="landingSistema" />
      </main>
      <PublicFooter />
    </div>
  );
}
```

**NOTA:** Como passar o namespace para os componentes? Cada componente já aceita `useTranslation('landing')` — preciso torná-lo configurável. Abordagem mais limpa: criar um wrapper que passa `namespace` como prop OU cada landing tem seu próprio i18n namespace e os componentes já são adaptados para isso.

**Abordagem recomendada (mínima mudança):** Os componentes já leem de `t()` com fallback. Basta criar as novas landing pages como componentes independentes que importam os mesmos componentes de secção mas com `useTranslation('landingIa')` etc. Cada secção lê do namespace correspondente. As chaves que não existirem no namespace específico caem no `fallbackLng: 'pt-BR'` ou usam o `|| 'fallback'` inline.

**Simplificação:** Os componentes de secção atuais usam `useTranslation('landing')`. Para as novas landings, vou usar `useTranslation('landingIa')` etc. Mas isso significa que os componentes de secção precisam aceitar um namespace prop. 

**Solução mais simples ainda:** Criar 3 novos ficheiros completos que importam os mesmos componentes visuais mas com um wrapper `useTranslation`. Cada landing page define seu próprio layout e ordem de secções, todas usando t() do seu namespace.

  // DON'T provide a landing namespace override, we use a context.
  // ULTRA SIMPLE: we just use the existing landing components as-is,
  // BUT we change the i18n namespace at the page level.
