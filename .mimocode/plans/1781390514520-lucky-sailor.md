# Plano de Otimização de Performance — Catequese Viva

## Diagnóstico

Com o banco de dados PostgreSQL em região diferente (>20ms de latência por query), **cada round-trip ao banco custa pelo menos 20ms**. O problema não é o processamento no servidor — é o **número excessivo de queries por página**, que multiplica essa latência.

### Raiz do problema
- Páginas comuns fazem **8-28 queries** ao banco por carregamento
- Com ~20ms de latência, uma página com 12 queries gasta **240ms só em network overhead**
- Somando execução SQL + serialização, o total facilmente ultrapassa **1-3 segundos**

### Problemas críticos encontrados (ordenados por impacto × esforço)

| # | Problema | Round-trips extra | Impacto |
|---|----------|------------------|---------|
| 1 | Índices em falta (ContentItem, SacramentalJourney, SacramentalMilestone) | — (não é round-trip, mas full-table scan é caríssimo com DB remoto) | Todas as queries dessas tabelas |
| 2 | N+1 queries em `getCurrentUserContext` (userContext.ts:75-92) | +N queries por diocese | Todas as páginas (carregado no AppShell) |
| 3 | Dashboard institucional: query sequencial fora do Promise.all (institutionalDashboardOps.ts:779-787) | +1 query sequencial (bloqueante) | Dashboard institucional |
| 4 | 28 queries individuais no getInstitutionalOverview — muitos counts poderiam ser consolidados | 14-28 round-trips extras | Dashboard institucional |
| 5 | Duplicação de scope resolution (Membership.findMany) em 9+ operações | 1-3 queries duplicadas por página | Todas as páginas |
| 6 | Sem paginação em 7 endpoints de listagem (carrega TODOS os registos) | Transferência massiva de dados + DB sem limites | Páginas de listagem |
| 7 | ClassDetailPage carrega 4 queries com dados duplicados | 3 queries redundantes | Página de detalhe de turma |
| 8 | Frontend: zero lazy loading nas rotas do app (50+ páginas no bundle inicial) | Bundle inicial enorme (não DB mas impacta primeiro load) | Primeiro carregamento |

### Fase 2: Corrigir N+1 em `getCurrentUserContext`

**Ficheiro**: `src/server/operations/userContext.ts:72-92`

**Problema**: Para DIOCESE_ADMIN, faz `N` chamadas individuais `Parish.findUnique()` em loop.

**Solução**: Substituir o loop por um único `findMany`:

```typescript
// ANTES (linhas 72-92):
for (const parishId of dioceseParishIds) {
  if (existingIds.has(parishId)) continue;
  const parish = await context.entities.Parish.findUnique({ ... });
  if (!parish) continue;
  result.push({ ... });
}

// DEPOIS:
const dioceseParishes = await context.entities.Parish.findMany({
  where: { id: { in: dioceseParishIds.filter(id => !existingIds.has(id)) } },
  select: { id: true, name: true, type: true },
});
for (const parish of dioceseParishes) {
  result.push({ ... });
}
```

**Impacto**: Para diocese com 50 paróquias: passa de 50 queries para 1. Economia de ~980ms de network overhead.

**Verificação**: Login como DIOCESE_ADMIN, navegar entre páginas — o AppShell (que chama `getCurrentUserContext`) carrega instantaneamente.

A query atual em linhas 779-787 deve ser movida para o `Promise.all` das linhas 241-280 (adicionar como 29º item do array).

#### 3b. Consolidar counts de ClassEnrollment (linhas 243-252)

**Problema**: 4 chamadas `ClassEnrollment.count()` separadas — cada uma é um round-trip.

**Solução**: Substituir 4 counts por 1 `groupBy`:

```typescript
// Consolidar estes 4 counts em 1:
// activeEnrollments, previousEnrollments, newEnrollments, droppedEnrollments

const enrollmentCounts = await context.entities.ClassEnrollment.groupBy({
  by: ['status'],
  where: { parishId: { in: parishIds }, status: { in: ['ENROLLED', 'DROPPED'] } },
  _count: { id: true },
});
```

**Impacto**: Reduz ~3 round-trips no dashboard institucional (~60ms).

**Verificação**: Abrir dashboard institucional, verificar que os contadores estão corretos.

### Fase 4: Cache de scope resolution por request

**Ficheiro**: Novo ficheiro `src/server/operations/sharedScope.ts`

**Problema**: Cada operação duplica `Membership.findMany({ userId, status: ACTIVE })` — numa página como DashboardPage, `getDashboardStats` e `getCurrentUserContext` cada um faz esta query.

**Solução**: Criar um módulo com cache por request usando `WeakMap` (padrão já usado em `searchOperations.ts`):

```typescript
// src/server/operations/sharedScope.ts
const scopeCache = new WeakMap<object, { parishIds: string[]; roles: string[]; memberships: any[] }>();

export async function resolveUserScope(context: any) {
  const cacheKey = context.entities;
  if (scopeCache.has(cacheKey)) return scopeCache.get(cacheKey)!;
  
  // Fazer Membership.findMany UMA vez
  // Calcular parishIds, roles, personal workspace, diocese expansion
  // Guardar em scopeCache
  scopeCache.set(cacheKey, result);
  return result;
}
```

Depois substituir nos ficheiros que duplicam esta lógica:
- `dashboardOperations.ts:9-42`
- `classOperations.ts:53-113`
- `catechumenOperations.ts:13-38`
- `familyOperations.ts:13-38`
- `contentOperations.ts:27-44`
- `sacramentOperations.ts:7-34`
- `conversationOperations.ts:13-38`
- `searchOperations.ts:31-54`

**Impacto**: Elimina 1-3 queries Membership duplicadas por cada página. Com 10+ páginas diferentes, a economia acumulada é enorme.

**Verificação**: Testar 3-4 páginas diferentes, confirmar que scope resolve corretamente e que não há regressão de permissões.
